# ADR-0003: Phase 1のブラウザー／プロファイル検出

- 状態: 採用
- 日付: 2026-07-24

## 背景

Chrome、Edge、Firefoxは複数プロファイルを持ち、既定のディレクトリー名だけでは列挙できません。また、ポリシーによる保存先変更、メタデータ破損、リパースポイント、ブラウザー派生プロセスの誤検出を考慮する必要があります。

Phase 1は読み取り専用の検出に限定し、バックアップ対象ファイルのコピーや認証情報処理は行いません。

## 決定

1. `Domain`にブラウザー、インストール、プロファイル、容量、プロセス照合のモデルと抽象を置く。
2. `Application`の`BrowserDiscoveryService`がアダプター、容量見積もり、実行中判定をまとめ、個別の読み取り失敗を非致命的な問題として扱う。
3. Chrome / EdgeはHKCU、HKLMの`UserDataDir`、標準パスの順で候補を作り、既知の変数だけを展開する。
4. Chromiumの主経路は`Local State`の`profile.info_cache`とし、読めない場合だけ直下の特徴ファイルでフォールバックする。
5. Firefoxは`profiles.ini`を主経路、`installs.ini`を既定判定の補助とし、読めない場合だけ`Profiles`直下の特徴ファイルでフォールバックする。
6. Guest / Systemプロファイルとリパースポイントを既定で除外する。容量集計でもリンク先を追跡しない。
7. プロセス名だけでは実行中扱いにせず、既知の実行ファイル完全パスと一致したプロセスだけを対象にする。
8. ファイル走査はUIスレッド外で行い、容量見積もりは最大3並列とする。
9. UIにはユーザー名を含み得る完全パスを出さず、表示名、内部名、既定、検出確度、実行中、推定容量だけを表示する。
10. 本体に外部NuGetパッケージを追加せず、.NET標準APIと手動構成を使用する。

## 根拠

- Chromium公式資料ではUser Data配下にプロファイルサブディレクトリーが置かれ、通常のディレクトリー名だけへ依存できない。
- Edgeの公式ポリシー資料は`UserDataDir`と複数のパス変数を定義している。
- Firefox公式資料は複数プロファイルがそれぞれ設定・履歴等を分離して保持することを示している。
- 容量と実行中状態は選択前の判断材料になる一方、検出段階で内容を変更する理由はない。

## 影響

- ポリシーやINIに明示された場所以外を広域探索しない。
- 読めない項目はスキップし、見積もりが不完全であることをUIへ伝える。
- 独自配置のブラウザー実行ファイルは、既知パスに一致しなければ実行中と判定できない場合がある。
- Beta / Dev / CanaryなどStable以外のChromiumチャンネルはPhase 1対象外とする。
