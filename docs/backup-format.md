# BVB暗号化バックアップ形式 v2

## 状態と互換性

Y-TEC Browser Capsule 1.1.0以降が新規作成する形式です。バックアップは
`.bvb`、対応する復元キーファイルは`.ybckey`です。両方がそろった場合
だけ復元できます。

1.0.0以前のBVB v1は読み取りと復元だけを維持します。v1の仕様は
[backup-format-v1.md](backup-format-v1.md)を参照してください。1.1.0以降の
製品UIはv1を新規作成しません。

## 暗号方式

- 暗号: AES-256-GCM
- コンテンツ鍵: バックアップごとにCSPRNGで生成する256-bit鍵
- 鍵識別子: `SHA-256(コンテンツ鍵)`
- 既定チャンク: 4 MiB（許容64 KiB〜16 MiB）
- nonce: バックアップごとの乱数4バイト + 64-bitチャンク番号
- tag: 16バイト
- AAD: `SHA-256(平文ヘッダー82バイト)` + チャンクフレームヘッダー16バイト
- ファイルハッシュ: SHA-256

コンテンツ鍵は`.ybckey`へ保存します。キーファイル自体は暗号化されず、
バックアップを開く秘密情報として扱います。アプリ内の固定鍵、端末固定鍵、
回避用バックドアはありません。別PCへは`.bvb`と`.ybckey`を移せます。

## BVB v2平文ヘッダー

固定長82バイトです。整数は特記がなければlittle-endian、UUIDはRFC 4122
big-endianです。

| Offset | Size | 内容 |
| ---: | ---: | --- |
| 0 | 8 | Magic `YTECBVB\0` |
| 8 | 2 | フォーマットバージョン（2） |
| 10 | 2 | ヘッダー長（82） |
| 12 | 2 | Key source ID（2 = recovery key file） |
| 14 | 2 | Cipher ID（1 = AES-256-GCM） |
| 16 | 32 | 復元キー識別子 `SHA-256(key)` |
| 48 | 4 | 予約（0） |
| 52 | 4 | 平文チャンクサイズ |
| 56 | 4 | nonce prefix |
| 60 | 16 | Backup ID |
| 76 | 2 | 最小アプリmajor |
| 78 | 2 | 最小アプリminor |
| 80 | 2 | 最小アプリbuild |

PC名、Windowsユーザー名、プロファイル名、パス、ファイル一覧は平文
ヘッダーへ入れず、暗号化マニフェストだけへ保存します。

## `.ybckey` v1

固定長92バイトです。

| Offset | Size | 内容 |
| ---: | ---: | --- |
| 0 | 8 | Magic `YTECKEY\0` |
| 8 | 2 | キーファイルバージョン（1） |
| 10 | 2 | ファイル長（92） |
| 12 | 16 | 対応するBackup ID |
| 28 | 32 | AES-256-GCMコンテンツ鍵 |
| 60 | 32 | `SHA-256(bytes[0..60])` |

Backup ID、チェックサム、BVBヘッダーの鍵識別子を固定時間比較で確認します。
別バックアップのキー、改ざんキー、欠損キーは同じ一般エラーで拒否します。
キーの値やパスはログへ出しません。

## 暗号チャンク

ヘッダー直後に次のフレームを連続して格納します。

```text
uint64 chunkIndex
uint32 plaintextLength
byte   flags        // bit 0 = final
byte[3] reserved    // すべて0
byte[plaintextLength] ciphertext
byte[16] tag
```

チャンク番号は0から単調増加し、nonceは
`noncePrefix[4] || chunkIndexBigEndian[8]`です。最終フレームは必須で、
末尾追加、欠落、重複、順序変更、切断を拒否します。

## 暗号化された逐次エントリー領域

内部ストリーム形式はv1を継続します。Magicは`YBVENTR\0`、内部versionは
1です。各ファイルは正規相対パス、宣言長、内容、SHA-256を持ち、末尾の
暗号化JSONマニフェストはBVB Format Version 2、Backup ID、作成日時、
環境ID、プロファイル、コンポーネント、CSV状態を持ちます。

標準ZIPや平文集約アーカイブは作りません。エントリーパスは絶対パス、
UNC、`..`、ADS、予約名、制御文字、大文字小文字衝突を拒否します。復元時は
復元ルートとリパースポイントを再検証します。

## 上限

- エントリー数: 100,000
- 暗号化マニフェスト平文: 16 MiB
- 暗号チャンク: 64 KiB〜16 MiB
- 個別ファイル長: 64 GiB
- 全ファイル合計: 2 TiB

ファイル全体をメモリへ読み込まず、128 KiB単位で処理します。

## 完成トランザクション

1. `.ybckey.partial`へ復元キーを書き、ディスクへflushする。
2. `.bvb.partial`へヘッダーと暗号ストリームを書き、ディスクへflushする。
3. `.bvb.partial`を`.ybckey.partial`で先頭から完全検証する。
4. キーを`.ybckey`へ、続いてバックアップを`.bvb`へ上書きなしで移動する。
5. 失敗・キャンセル時は両partialと、途中で完成名へ移したキーを削除する。

既存の完成ファイルは上書きしません。完成BVBだけが残ってキーがない状態を
作らない順序にしています。

## 検証済み展開

- 全暗号チャンク、全エントリー、マニフェストを最後まで認証する。
- 展開先は空のローカル通常フォルダーに限定する。
- 選択外エントリーも認証と構造検証を省略しない。
- 保存パスワードCSVは公式インポート時だけACL制限領域へ一時展開する。
- 保護対象ファイル名を含むバックアップは、復元およびCSV取り出し前に拒否する。BVB v1/v2の保存形式、暗号方式、復元キー形式は変更しない。
- 展開ファイルの長さとSHA-256を再確認する。

## バージョン規則

- 読取側はBVB v1とv2だけを明示的に受理する。
- v2にはRecovery Key File、v1にはLegacy Passphraseだけを受理する。
- 未知のVersion、Key source/KDF ID、Cipher ID、ヘッダー長を推測で開かない。
